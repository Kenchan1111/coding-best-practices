# Choix de design

Un trigger doit aider le LLM pendant le coding, pas devenir une page de doctrine ignoree.

Chaque trigger contient donc :
- `phase` : quand agir, souvent `before_edit_or_bash`
- `fires_on` : signaux concrets dans chemin, code, commande ou demande utilisateur
- `calls_checks` : check principal plus checks voisins, pour proteger l'invariant complet
- `suppress_when` : cas ou ne pas declencher, pour limiter le bruit
- `preflight_budget` : budget court, 45 ou 60 secondes
- une phrase obligatoire de preflight a produire avant l'edit ou le finding

# Limites

- P3 ne branche pas encore les triggers dans un generateur executable.
- P4 doit verifier automatiquement que tous les `calls_checks` existent.
- Le smoke test dynamique P7 devra prouver que le LLM applique au moins un preflight avant coding, pas seulement qu'il lit le trigger.
